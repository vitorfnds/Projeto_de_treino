- lógica de programação
- modularização
- persistência de dados
- desacoplamento entre sistemas
- estruturação de código
- manutenção de software
- evolução sustentável de projetos

O desenvolvimento do sistema deve acompanhar
o crescimento do conhecimento durante o aprendizado.

Por esse motivo:
- a arquitetura poderá evoluir gradualmente
- nomes de arquivos poderão mudar
- nomes de funções poderão mudar
- estruturas poderão ser reorganizadas
- responsabilidades poderão ser refinadas
- sistemas poderão ser separados futuramente

O projeto não busca criar imediatamente
uma arquitetura definitiva ou perfeita.

O foco principal é:
- compreender os conceitos
- aprender boas práticas
- evoluir gradualmente

- desenvolver experiência prática

As implementações devem priorizar:
- clareza
- simplicidade

Refatorações, reorganizações e melhorias
devem acontecer conforme:
- o conhecimento evoluir
- novas necessidades surgirem
- padrões reais aparecerem
- o sistema crescer gradualmente

O objetivo não é evitar mudanças,

-------------------------------------------

    SEPARAÇÃO ENTRE INTERFACE E LÓGICA

O sistema deve manter separação clara entre:
- interface
- entrada de dados
- exibição visual
- processamento interno
- regras dos jogos

Inicialmente o projeto funcionará em console.

Porém, toda a arquitetura deve permanecer preparada
para futura evolução para:
- interfaces gráficas
- botões interativos
- janelas
- aplicações web
- múltiplas plataformas

Por esse motivo:
- a lógica do sistema não deve depender diretamente do console
- regras dos jogos não devem utilizar `input()`
- regras dos jogos não devem utilizar `print()`
- regras internas não devem depender de menus do terminal
- a lógica não deve controlar elementos visuais
- a lógica não deve depender da tecnologia da interface

O console deve funcionar apenas como:
- camada de interface
- captura de entrada do usuário
- exibição de informações
- navegação visual temporária

A lógica do sistema deve:
- receber dados
- processar regras
- retornar resultados
- permanecer independente da interface utilizada

Exemplo incorreto:

def validar():
    numero = input("Digite um número: ")

    if numero == "5":
        print("Acertou")

Problemas deste modelo:
- lógica depende diretamente do terminal
- dificulta reutilização
- dificulta manutenção
- dificulta migração futura para GUI
- dificulta migração futura para web

Exemplo correto:

def validar(numero):
    return numero == "5"

Neste modelo:
- a lógica permanece desacoplada
- a interface controla entrada de dados
- a interface controla exibição das mensagens
- o sistema pode reutilizar a mesma lógica em:

  - console
  - interface gráfica
  - aplicações web
  - futuras plataformas

A interface deve possuir responsabilidade apenas por:
- capturar ações do usuário
- enviar dados para a lógica
- exibir resultados retornados pelo sistema
- controlar navegação visual

As regras internas devem permanecer independentes
da tecnologia visual utilizada pelo projeto.

O objetivo principal é garantir:
- baixo acoplamento
- facilidade de manutenção
- reutilização da lógica
- evolução sustentável do sistema
- compatibilidade futura com interfaces gráficas

Evitar:
- lógica misturada com interface
- regras utilizando `print()`
- regras utilizando `input()`
- jogos dependendo diretamente do terminal
- navegação espalhada entre múltiplos sistemas
- código visual misturado com processamento interno

    ARQUITETURA DAS INTERFACES

A lógica principal do sistema deve permanecer centralizada
e independente da interface utilizada.

As interfaces devem funcionar apenas como camadas responsáveis por:
- exibir informações
- capturar ações do usuário
- enviar ações para o sistema
- apresentar resultados

Exemplo conceitual da arquitetura:

                    ┌───────────────────────┐
                    │     LÓGICA REAL       │
                    │      DO SISTEMA       │
                    └───────────────────────┘
                               ▲
                               │
                ┌──────────────┼──────────────┐
                │              │              │
                │              │              │

     ┌────────────────┐ ┌────────────────┐ ┌────────────────┐
     │   INTERFACE    │ │ INTERFACE GUI  │ │ INTERFACE WEB  │
     │    CONSOLE     │ │ BOTÕES/JANELAS │ │   NAVEGADOR    │
     └────────────────┘ └────────────────┘ └────────────────┘

Neste modelo:
- todas as interfaces utilizam a mesma lógica interna
- apenas a forma de interação do usuário muda
- regras dos jogos permanecem reutilizáveis
- persistência continua compartilhada
- rankings continuam compartilhados
- sistema de usuários continua compartilhado
- moedas continuam compartilhadas

Exemplo:

    - No console:
      o usuário digita um número

    - Na interface gráfica:
      o usuário clica em um botão

    - Na interface web:
      o usuário interage pelo navegador

    - Nos três casos:
      a ação interna do sistema continua sendo a mesma
      apenas a interface de entrada muda

O objetivo desta arquitetura é permitir:
- reutilização da lógica
- baixo acoplamento
- facilidade de manutenção
- evolução gradual do sistema
- compatibilidade futura com múltiplas interfaces

As interfaces devem funcionar apenas como:
- camada visual
- camada de interação
- camada de navegação
- camada de comunicação com o usuário

Enquanto:
- regras
- lógica
- persistência
- sistemas internos

devem permanecer independentes da interface.

-------------------------------------------

    CONTROLE DE NAVEGAÇÃO E INTERFACE

O sistema funcionará inicialmente em console,
utilizando menus baseados em opções escolhidas pelo usuário.

Exemplo:

1 - Login
2 - Criar Usuário
3 - Sair

As telas do console devem ser apresentadas em uma caixa
que se ajusta automaticamente ao tamanho do texto.
O tamanho da caixa deve ser baseado na linha mais longa
mais uma margem de espaçamento.

Exemplo de tela dinâmica:

    |------------------|
    |    TELA LOGIN    |
    |                  |
    | 1) Fazer login   |
    | 2) Criar Usuário |
    | 3) Sair          |
    |------------------|

O título da tela deve permanecer alinhado e centralizado
no topo da caixa, conforme o exemplo.
Essa caixa deve crescer quando o texto interno for maior,
sem quebrar a borda ou deixar linhas estourarem.

Esse modelo é válido para o projeto atual
e não representa acoplamento incorreto com o console.

A utilização de:
- números
- menus
- opções digitadas
- escolhas do usuário

faz parte apenas da interface atual do sistema.

A arquitetura deve permitir que,
futuramente, o console possa ser substituído por:
- botões interativos
- janelas gráficas
- interfaces web
- outras formas de interação

sem necessidade de alterar:
- regras dos jogos
- lógica interna
- persistência
- sistema de usuários
- rankings
- moedas
- regras das partidas

Exemplo no console:

    - usuário digita:
      1

    - A interface interpreta:
      abrir tela de login

Exemplo em interface gráfica futura:

    - usuário clica no botão:
      "Login"

    - A interface interpreta:
      abrir tela de login

Nos dois casos:
- a ação interna continua sendo a mesma
- apenas a forma de interação muda

As telas não devem possuir navegação espalhada
ou dependência direta entre si.

Exemplo incorreto:

def tela_login():
    tela_menu()

Esse modelo aumenta:
- acoplamento
- dependência entre telas
- dificuldade de manutenção
- dificuldade de adaptação futura para GUI

O ideal é que cada tela:
- execute apenas sua responsabilidade
- processe a interação atual
- retorne o próximo fluxo do sistema

Exemplo conceitual:

def tela_login():
    return "menu"

Neste modelo:
- a tela não controla diretamente outra tela
- a navegação permanece organizada
- o sistema continua desacoplado da interface

O fluxo principal do sistema poderá futuramente
ser controlado por um sistema central de navegação.

-------------------------------------------

    TELA LOGIN

Responsável pela autenticação dos usuários.

Campos:

- usuário
- senha

Regras:

- máximo de 3 tentativas
- usuário inexistente gera nova tentativa
- senha incorreta gera nova tentativa
- o usuário não diferencia letras maiúsculas e minúsculas
- espaços no início e no final do usuário devem ser removidos automaticamente antes da validação
- após 3 falhas retorna para Tela Inicial

Login válido:

→ Menu Principal

-------------------------------------------

    TELA CRIAR USUÁRIO

Responsável pelo cadastro de novos usuários.

Campos:

- usuário
- senha

Regras do usuário:

- deve ser único
- a verificação de usuário único não diferencia letras maiúsculas e minúsculas
- mínimo de 2 caracteres
- máximo de 20 caracteres
- não pode conter espaços
- deve conter apenas letras e números
- espaços no início e no final devem ser removidos automaticamente antes da validação

Observação: o trim() deve ser aplicado apenas nas bordas antes da validação. Espaços internos no nome de usuário são inválidos. Uma validação adequada pode ser feita com algo como `^[A-Za-z0-9]{2,20}$`.

A unicidade do usuário deve ser validada utilizando
uma versão normalizada do nome de usuário.

Durante essa validação não devem ser consideradas
diferenças entre letras maiúsculas e minúsculas.

Exemplo:

- vitor
- Vitor
- VITOR
- ViToR

Representam o mesmo usuário para fins de cadastro.

Caso qualquer uma dessas variações já exista,
o cadastro de uma nova variação deve ser recusado.

Regras da senha:

- mínimo de 4 caracteres
- máximo de 20 caracteres
- não pode conter espaços
- espaços no início e no final devem ser removidos automaticamente antes da validação

Observação: as senhas não devem ser armazenadas em texto simples no arquivo de dados. No futuro, utilize hashing seguro para proteger as senhas dos usuários.

Regras gerais:

- usuário duplicado gera mensagem de erro
- novo usuário inicia com 10 moedas

Mensagens de validação:

- Usuário deve possuir entre 2 e 20 caracteres.
- Usuário não pode conter espaços.
- Usuário deve conter apenas letras e números.
- Usuário já existe.
- Senha deve possuir entre 4 e 20 caracteres.
- Senha não pode conter espaços.

Após cadastro concluído:

→ Tela Login

Opção disponível:

- Voltar

Retorna para Tela Inicial

    TIPOS DE USUÁRIOS

O usuário é global no sistema.

Moedas, gastos, recordes e progressos
devem funcionar globalmente entre todos os jogos.

Inicialmente existirão 2 tipos de usuários:

1 - Usuário Teste

- já existe no sistema
- possui mais moedas
- utilizado para testes
- possui vantagens para facilitar validações
- não precisa ser criado manualmente

O usuário teste deve ser criado automaticamente
pelo sistema caso ele ainda não exista no banco de dados.

Os valores poderão ser alterados futuramente
conforme o balanceamento do sistema.

2 - Usuário Comum

- segue todas as regras normais do sistema
- não possui vantagens especiais
- respeita todas as regras dos jogos
- precisa ser criado pelo jogador

    BANCO DE DADOS

Inicialmente o sistema utilizará arquivos JSON.

Objetivos:
- simplicidade
- organização
- aprendizado
- facilidade de manutenção

Exemplo:

├── banco_dados
│   ├── usuarios.json
│   ├── ranking.json
│   ├── configuracoes.json

Os nomes dos arquivos são apenas exemplos.

O sistema poderá futuramente:
- reorganizar arquivos
- separar novos dados
- migrar para outro banco

A manipulação dos arquivos JSON
deve permanecer centralizada
em um sistema responsável apenas pela persistência.

Inicialmente o foco é evitar
que múltiplos sistemas manipulem arquivos diretamente
de forma espalhada pelo projeto.

Exemplo incorreto:
- login acessando JSON diretamente
- ranking acessando JSON diretamente
- jogos salvando arquivos diretamente
- moedas manipulando arquivos diretamente

Esse tipo de abordagem pode gerar:
- repetição de código
- dificuldade de manutenção
- inconsistência de dados
- aumento do acoplamento
- dificuldade futura de reorganização

O ideal é que os sistemas utilizem
uma camada responsável apenas por:
- carregar dados
- salvar dados
- criar arquivos necessários
- validar existência básica dos arquivos

Sem misturar:
- regras de jogo
- navegação
- interface
- lógica específica
- comportamento das partidas

Exemplo conceitual:

sistema
    ├── persistencia.py

Responsável por:
- leitura de arquivos
- escrita de arquivos
- carregamento de dados
- salvamento de dados

Os demais sistemas devem utilizar
a persistência de forma indireta,
evitando acesso direto aos arquivos.

    FUNÇÕES

Funções devem possuir:
- responsabilidade clara
- objetivo específico
- comportamento previsível

Evitar funções excessivamente longas
ou que misturem múltiplas responsabilidades.

Se uma função começar a crescer demais,
avaliar separação em funções menores.

-------------------------------------------

    RESPONSABILIDADE DOS ARQUIVOS

Cada arquivo deve possuir
uma responsabilidade principal bem definida.

Evitar arquivos que misturem:
- interface
- lógica
- persistência
- navegação
- regras específicas dos jogos

-------------------------------------------

    ACOPLAMENTO ENTRE SISTEMAS

Evitar dependências circulares entre módulos.

Sistemas globais não devem depender
diretamente das regras específicas dos jogos.

Os jogos devem utilizar os sistemas globais,
mas os sistemas globais devem permanecer desacoplados
das implementações específicas dos jogos.

-------------------------------------------

    GENERALIZAÇÃO PREMATURA

Não generalizar sistemas cedo demais.

Reutilizações, abstrações e estruturas genéricas
devem surgir apenas quando padrões reais
aparecerem no desenvolvimento do projeto.

Pequenas duplicações podem ser aceitáveis
quando evitarem abstrações prematuras
ou aumento desnecessário de complexidade.

-------------------------------------------

    IMPLEMENTAÇÕES FUTURAS

Não realizar suposições sobre funcionalidades,
regras ou estruturas futuras do sistema.

Implementações devem ser baseadas apenas
em requisitos, comportamentos e necessidades
já definidos no projeto.

Antes de implementar qualquer comportamento,
sempre validar se ele realmente já faz parte
das regras atuais do sistema.

-------------------------------------------

    LEGIBILIDADE DO CÓDIGO

Priorizar legibilidade e clareza
ao invés de soluções excessivamente complexas,
compactas ou difíceis de entender.

O código deve ser fácil de:
- ler
- entender
- modificar
- manter futuramente

-------------------------------------------

    CONFIGURAÇÕES E VALORES

Evitar valores fixos espalhados pelo sistema.

Valores importantes devem possuir:
- configuração
- constante
- estrutura centralizada

Exemplo:
- quantidade de moedas
- tentativas
- recompensas
- custos
- limites

-------------------------------------------

    OTIMIZAÇÕES

Não realizar otimizações prematuras.

Primeiro garantir:
- funcionamento correto
- organização
- clareza
- estabilidade

Otimizações devem acontecer apenas
quando houver necessidade real identificada.

-------------------------------------------

    COMPLEXIDADE DAS SOLUÇÕES

A complexidade da solução deve ser proporcional
ao tamanho real do problema.

Evitar arquiteturas complexas
para funcionalidades simples.

O projeto deve evoluir gradualmente,
acompanhando a necessidade real do sistema.

-------------------------------------------

    ANÁLISE ANTES DE IMPLEMENTAR

Sempre analisar antes de implementar:
- isso é realmente necessário agora?
- o sistema atual já resolve esse problema?
- a complexidade adicionada vale a pena?
- existe uma solução mais simples?
- essa separação realmente melhora o projeto?
- isso pode ser implementado futuramente?
- isso realmente já existe nas regras do projeto?
- estou implementando algo real
  ou apenas supondo um cenário futuro?

    REGRAS DE CONTEXTO E IMPLEMENTAÇÃO DA IA

A IA deve trabalhar exclusivamente
com base no projeto atual e no código existente.

Toda sugestão, implementação, correção,
refatoração, organização ou modificação
deve considerar apenas:
- regras já definidas
- estruturas já existentes
- código realmente presente no projeto
- comportamentos documentados
- funcionalidades já implementadas
- responsabilidades atuais do sistema

A IA não deve:
- supor existência de código
- imaginar estruturas
- presumir funcionalidades futuras
- criar cenários hipotéticos
- considerar comportamentos não documentados
- assumir implementações inexistentes

Evitar respostas contendo:
- "provavelmente"
- "talvez exista"
- "acredito que"
- "pode ser que"
- "normalmente projetos possuem"
- "geralmente isso fica em"
- "imagino que seu sistema tenha"

Toda análise deve ser baseada:
- no código realmente enviado
- na estrutura realmente existente
- nas regras documentadas do projeto
- nas implementações atuais do sistema

Caso determinada estrutura:
- não exista
- não tenha sido criada
- não tenha sido enviada
- não esteja documentada

a IA não deve:
- inventar
- presumir
- inferir automaticamente
- responder como se existisse

A IA deve sempre:
- respeitar a arquitetura atual do projeto
- manter consistência com o sistema existente
- reutilizar estruturas já implementadas
- evitar criação desnecessária de novos sistemas
- evitar alterações fora do escopo atual
- manter coerência com as regras do projeto

Implementações devem acontecer apenas:
- dentro do contexto atual do sistema
- dentro das regras existentes
- dentro da estrutura real do projeto
- dentro das responsabilidades já definidas

A IA deve considerar que possui acesso completo
ao projeto e ao código atual durante o desenvolvimento.

Portanto:
- não deve responder com hipóteses
- não deve responder com suposições
- não deve responder com possibilidades abstratas
- não deve responder com cenários imaginários

As respostas devem ser:
- diretas
- objetivas
- consistentes com o projeto
- alinhadas ao código existente
- baseadas apenas em informações reais do sistema

-------------------------------------------

    AUTORIZAÇÃO PARA CRIAÇÃO DE CÓDIGO

A IA não deve criar ou modificar código sem autorização explícita do desenvolvedor.

Antes de gerar código:
- oferecer orientação de como fazer
- sugerir a estrutura e abordagem
- explicar o passo a passo
- sugerir o código como exemplo
- aguardar aprovação e autorização do desenvolvedor

O desenvolvedor sempre deve ser quem:
- cria os arquivos
- escreve o código
- faz as modificações
- toma as decisões sobre arquitetura
- autoriza alterações

A IA funciona como professor:
- explica conceitos
- orienta o desenvolvedor
- sugere soluções
- valida código proposto
- mas nunca impõe mudanças sem consentimento
